# style-repaint

Use this skill when existing live-action footage, image assets, or rendered storyboards need to be converted into another art style (most commonly live-action to anime; also photorealistic to 2D, to cartoon-rendered 3D, to photorealistic 3D, between different animation/comic styles, and to live-action photorealism). You are the **style repaint director**—not a post-production step that slaps on filters, but someone directing shot by shot to "re-draw the same scene in the target style," while holding the line so characters stay recognizable and actions and emotions don't drift.

> **Environment adaptation**: The open-source solutions in the source methodology (AnimeGAN, VToonify, etc.) all perform "frame-by-frame style transfer on existing video" and generally carry commercial-use licensing restrictions; the style capabilities claimed by commercial APIs are mostly unverified marketing claims. This environment has no tools like img2img, style filters, or ControlNet/LoRA that "change the style directly on the original pixels," but when generating video you can pass the source clip nodes as input references to `generate_video_v3` (see "Generation Mode Selection"), at roughly twice the cost of the pure-text path. The technical path is **content parsing + regeneration in the target style**; the pipeline closely resembles `aspect-reframe` (landscape/portrait conversion)—both first slice out real shot clips, then judge a processing strategy shot by shot, then use screenshots for image-to-image regeneration—the only difference is that `aspect-reframe` changes composition while this skill changes art style, and art-style changes involve more distortion risk points (temporal consistency, multi-character anchor confusion, hands/text and other high-risk elements), so shot-by-shot judgment needs to be finer than for `aspect-reframe`. **Consequences the user must explicitly accept**: even in source-footage-input mode, the output is still "another art-style version of the same scene," preserving character identity, composition, action, and emotion, but it is **not a frame-by-frame pixel conversion of the original footage** and cannot align perfectly with the original frames—this is dictated by the nature of "regeneration in a different art style," not something the choice of cost mode can change.

## Process Overview (6 pause points, done in order)

0. **Create the task** (`task_create_v2`): create one progress task for this repaint job; `task_content` points to the file path of the shot ledger to be produced—a one-time pointer, not a step-by-step checklist. At the end of the full process, mark it complete with `task_update_v2`.
1. **Determine input form and target style**: live-action footage / image assets / rendered storyboards; classify the target art style into the corresponding category under "Style Category Differences"—different categories carry different risks and treatments; when converting to cartoon-rendered 3D, additionally consult "Pixar-style 3D cartoon rendering reference techniques"; for live-action/photorealistic styles, do not apply the preset vocabulary—generate directly from the user's description.
2. **Determine the generation mode** (see "Generation Mode Selection" for details) → **Pause point 1**. This must be done before touching `analyze_video`/`edit_video`—don't finish analyzing and slicing and only then come back to ask; the mode determines the slicing precision of the next step. Image/storyboard inputs have no source video and can only use Mode 2, so keep confirmation brief.
3. **Obtain the source content structure and slice it** (see "Input Slicing" for details):
   - Video → run `analyze_video` calibrated against the hint (>15 seconds: rough-cut first, then analyze each segment in fine detail; ≤15 seconds: go straight to fine analysis), with precision depth determined by the mode selected in step 2; then use `edit_video` to cut out the source clip node of each real shot at precise time points.
   - Image/storyboard → read the existing composition and content description directly, skipping analysis and slicing.
4. **Analyze content shot by shot and build the shot ledger** (see "Shot Content Analysis and Ledger" for details, `write_file_v2`): record not just the narrow fields needed for strategy judgment, but also the characters present, key actions, key narrative information, and scene identifiers; this step only extracts "what is depicted"—style information is discarded (the style will be replaced).
5. **Apply the decision table shot by shot** (see "Repaint Strategy Judgment" for details), appending the judged strategies (single-frame / multi-frame / multi-character coordinated anchoring / high-risk element reinforcement; multiple selections allowed) and the number and positions of frames to be captured into the same shot ledger → **Pause point 2**: use `ask_human` to present the complete shot ledger (content fields + decision fields) for confirmation—a misjudged strategy leads to wasted regeneration of the entire batch, the same logic as with `aspect-reframe`.
6. **(When in Mode 2 and important characters/scenes are involved) Confirm anchor sources** (see "Confirming Anchor Sources for Important Characters/Scenes" for details) → **Pause point 3**.
7. **Establish the style bible + generate character/scene style anchors** (see "Core Mechanism" for details) → **Pause point 4** (the most critical one).
8. **Repaint key frames shot by shot** (`generate_image_v3`, used in Mode 2; in Mode 1 the next step uses the source clips directly as reference, so no separate key-frame repainting is needed): following the judged strategies recorded in the shot ledger, capture the corresponding number of frames per shot (single-frame or multi-frame) as the image input (image-to-image). **Check each frame for usability as soon as it is captured** (clear with no motion blur, subject not cropped or occluded out of frame, angle and pose recognizable)—multi-frame repainting is especially prone to "most frames are fine, a few frames are problematic"; do not make do with unusable frames—recapture a frame near that key point (e.g., ±0.2–0.5 seconds), confirm it is usable, and only then use it; never feed a problematic screenshot straight into image-to-image. Once usability is confirmed, repaint on the basis of the real screenshot according to the style bible, rather than discarding the screenshot and generating from scratch from text alone; at the same time, apply the corresponding character/scene style anchors, along with the special handling for multi-character coordinated anchoring / high-risk element reinforcement. For consecutive shots in the same scene, additionally reference the repainted tail frame of the previous shot to suppress discontinuities (a free extra measure) → **Pause point 5**: spot-check the repainted frames of the first few shots, confirming the art style has landed, characters are recognizable, and the composition has not lost key information; only after passing, release for batch processing.
9. **Generate the style-transferred videos** (`generate_video_v3`): Mode 1 uses the original clips cut by `edit_video` as the input reference (together with the style bible + character anchors; when the scene is the same, the previous shot's last frame may also be added); Mode 2 uses the style-transferred keyframes from step 8 (a single frame or a multi-frame sequence) as the visual anchor. In both modes, the actions and emotional beats continue from what the shot ledger records, without re-performing them. **The generated duration must equal the time-interval duration recorded for that shot in the ledger**; you cannot just let the generation tool hand back its default one-or-two-second short clip — the final composite is stitched together in the original shot order, so if one shot comes out too short, the overall rhythm and duration of the stitched result won't match the original video.
   - **The Mode 1 prompt must put bounds on "what the original video is referenced for"**: the original clip carries the old art style; if the prompt doesn't explicitly exclude it, the model can easily drag the old style's visual features along with it (the style gets diluted by the original video). In the wording, explicitly split it into two parts: first state "reference only the original video's camera movement, character actions/performance, and compositional rhythm; do not reference its visual style/colors/rendering texture," then separately and in detail give the style bible description plus the corresponding character/scene style anchor references — do not vaguely blur "referencing the original video" and "the target art style" together in a single sentence.
   - **How to write dialogue into the prompt**: `generate_video_v3` has no pass-through capability for the original audio track; visuals and sound are regenerated together end-to-end — dialogue can only be guided through textual description, and there is an inherent risk of the model "improvising" and rewriting it. Risk-reducing wording: list the dialogue recorded in the ledger verbatim in quotation marks, followed by an explicit line "generate exactly this, verbatim; do not rewrite the wording, tone, or compress/stretch the speaking pace" — this is an **exclusionary instruction**, not a content description for the model to "perform by reference." For shots without dialogue, honestly write "no dialogue."
   - **How to write BGM/sound effects**: don't demand frame-by-frame reproduction of timbre/sound effects; describe only the emotional tone and the key sound-effect types, setting reasonable expectations rather than fabricating a precise audio description that can't be delivered.
10. **QC grading** (see "Consistency Check" for details): Error-grade items are sent straight back to step 8/9 for regeneration in the background and are not shown to the user; only Usable-grade and Excellent-grade items proceed to composition, and Usable-grade requires user confirmation.
11. **Composite** (`composite_video`) stitches the clips together in the original order, using only the segments that passed QC grading → **Pause point 6**: run an overall pass over temporal consistency, focusing on whether characters/art style stay coherent across shots.

Image/storyboard inputs enter through the read branch of step 3 (skipping analysis and slicing), but steps 1 and 2 still apply, and only Mode 2 can be used.

## Generation Mode Selection (original-video input / pure-text regeneration — choose one of the two, weighing cost vs. fidelity)

The two modes can be mixed shot by shot; they don't have to be uniform across the whole video:

| | **Mode 1: Original-Video Input** | **Mode 2: Pure-Text + Style-Anchor Regeneration** |
|---|---|---|
| Approach | Pass the original clip nodes cut by `edit_video` to `generate_video_v3` as input references, submitted together with the style bible + character style anchors, so the model applies the style on top of the original video's real actions/camera movement | The style-transferred keyframes (`generate_image_v3`) use that shot's screenshot as the image input and are repainted according to the style bible (image-to-image, not pure text generation); when driving `generate_video_v3`, do not pass the original video — "not passing the original" refers to the video-generation step not using the original video as reference; the keyframe transfer itself is still based on the screenshot |
| Cost | About 2× Mode 2 | Baseline cost |
| Help with temporal consistency | Greater — the model follows the original video's continuous motion, less prone to cross-shot jumps than "re-choreographing the action from anchor points" | Still has to be carried by the style bible + character anchors; higher risk of jumps |
| Fidelity | Higher for visuals — action details and camera-movement rhythm are closer to the original video; **but sound is not included**: `generate_video_v3` has no pass-through capability for the original audio track; in either mode, sound is regenerated end-to-end together with the visuals, so dialogue/sound effects carry the same drift risk — choosing Mode 1 does not mean the sound is a pass-through of the original video | Lower — it is "re-performing the same scene in a new art style" |
| Applicable scenarios | Protagonist close-ups, shots with high precision requirements for action/expressions, and high-risk categories such as conversion to photorealistic 3D rendering | Background/extra shots, limited budgets, or when the original video is itself a static image (no video available as input) |
| Precision required of "input slicing" | Only rough cutting is needed (clips ≤15 seconds can serve as references); fine-grained analysis is not mandatory | Fine-grained analysis must be completed to obtain accurate per-shot cut points; rough-cut segments cannot be used directly |

Default recommendation: for lower-/medium-risk categories such as live-action-to-anime / photoreal-to-2D and cartoon-rendered 3D conversions, Mode 2 is fine by default; **for the highest-risk category — conversion to photorealistic 3D rendering, confirmed by research to have no mature solution — Mode 1 is recommended first**, using the original video's actions as constraints to reduce the probability of structural drift.

## Input Slicing: hint Calibration + Fine-Grained Analysis + (Long Videos) Two-Stage Rough Cutting

**Step 1: First make a prior estimate of the shortest shot duration, and choose the `hint` parameter of `analyze_video` accordingly** — the hint is essentially a prior input of the "expected shortest shot duration," directly determining the sensitivity of cut-point detection:

| Prior shortest shot duration | hint |
|---|---|
| ≥5 seconds | 5 |
| 2–5 seconds | 3 |
| 1–2 seconds | 2 |
| <1 second | 1 (use with caution; prone to over-cutting) |

If the hint is finer than the actual shortest shot, subtle visual changes inside a continuous action will be misjudged as cut points; if it is coarser than the actual shortest shot, real short-shot cut points will be missed. **When no prior information is available, default to hint=2** — there is no need to stop and ask the user first just to estimate this value; when a clear prior exists, switch to the corresponding tier per the table above.

**The decision threshold is a hard 15 seconds, not "whether it feels short"**: only videos ≤15 seconds go through a single fine-grained analysis; **anything over 15 seconds (even a 20-second or 1-minute clip that "doesn't feel that long") must always go through a rough cut first** — do not skip it based on an intuitive judgment like "this one isn't long, so a rough cut probably isn't needed"; the reliability of fine-grained analysis is not guaranteed over spans beyond 15 seconds, and it tends to miss cuts (typical symptom: a single "shot" contains black screens, abrupt scene/character changes, and other obvious jump signals).

**Mandatory self-check before calling `analyze_video` (cannot be skipped; this is not a reminder but an action that must be performed explicitly)**:
1. First write out this video's **exact duration in seconds**, not a subjective judgment like "looks not long."
2. Determine whether that number is >15. **When it is >15 seconds, calling `analyze_video` directly on the full video is forbidden** — even if the content looks like it has "little scene change, so cutting probably isn't needed," a rough cut must be done first.
3. **Post-hoc verification (the last safety net)**: if the result of `analyze_video` has already been obtained, go back and check — was this call a single analysis made directly on a full video >15 seconds long (without a rough cut first)? If so, **that result is untrustworthy and must not be used directly for style transfer or for subsequent judgments**; you must return to "rough cut → fine-grained analysis segment by segment → precise slicing from the original video" and redo it.
4. **Common-sense check**: if the number of shots cut out is conspicuously small relative to the content type and duration (e.g., a one-minute dialogue/action scene yields only single-digit shots), first suspect "should a rough cut have been done but wasn't."
5. **Rough-cut results must not be used directly as the final shots (a more insidious form of missed work than "no rough cut at all")**: The sole purpose of the rough cut is to split the long video into a size the fine-grained analysis can handle; the segment boundaries returned by the rough cut itself are usually still coarse (a real case: for the same 110-second video, one run executed the full pipeline, performed fine-grained analysis on every rough segment, and produced 34 shots; on another run, after rough-cutting into 8 segments, only 2 segments were selected for fine-grained analysis while the other 6 had their rough-cut results used directly as shots, yielding only 16). Go back and check two things: ① whether every shot record in the final ledger corresponds to a separate `analyze_video` call made with the lowered hint (usually 2-3, not the 15 used for the rough cut); ② whether this fine-grained analysis was performed on every rough segment returned by the rough cut — you may not pick only the segments that "look complex/important" (e.g., fight scenes) and pass the rest off as shots using their rough-cut results. If either check fails, run the missing fine-grained analysis for the skipped rough segments.

**≤15 seconds**: Run `analyze_video` once on the whole video with the calibrated hint; the `source_start`/`source_end` of each returned shot are the accurate cut points and need no extra verification. Once you have the cut points, call `edit_video` directly to cut precisely — repaint judges whether the style lands shot by shot, and inaccurate cut points will scramble the units of judgment.

**>15 seconds**: Must be split into three steps; the third step goes back to the original video to cut, and you must not cut again on top of the rough segments:

1. **Rough cut**: Use a large hint (e.g., 15) to split the long video into several rough segments of ≤15 seconds; the goal is only to get it down to a size the fine-grained analysis can handle, not to make the cut points precise. Adjacent rough segments deliberately overlap by 1–2 seconds so the rough cut points do not land right in the middle of a real shot. **Rough cut point selection must also avoid places where dialogue carries over**: 15 seconds is a target, not a hard-locked integer — if there is dialogue within 1 second before or after a candidate cut point, move it away to avoid it; if you truly cannot find a point with no dialogue within 1 second on either side, relax it to no dialogue within 0.5 seconds on either side — cutting in the middle of a continuous line of dialogue means the "per-segment fine-grained analysis" lacks full context when analyzing each rough segment independently, which easily leads to errors.
2. **Per-segment fine-grained analysis**: For each rough segment, recalibrate the hint per the table above and run a separate fine-grained `analyze_video` to obtain the accurate cut points within that segment (timestamps relative to the rough segment's start) and content descriptions.
3. **Go back to the original video for precise cutting**: ⚠️ Add the rough segment's absolute start time in the original video to the timestamps from step 2 to convert them into absolute timestamps, then call `edit_video` on the **original video** — you must not cut again on top of the files produced by the rough cut, otherwise the cumulative timestamp error will drift further and further off toward the end.
   - **Deduplicate and merge overlapping intervals (a problem that has actually occurred: the previous/next shot's frames got mixed into the cut clips)**: Adjacent rough segments deliberately overlap by 1–2 seconds, and this overlap window gets independently detected once by each segment's fine-grained analysis, very likely reporting duplicate content or even two versions of the same real shot. Before converting to absolute timestamps and writing to the ledger, first check whether the time intervals of any two adjacent shots overlap each other — if they overlap, they must be merged into a single boundary; both versions may not be kept: take as authoritative the version that fully covers this window and whose cut point falls on a dialogue/action boundary, and directly discard the detection results from the other version that fall inside the overlap window. Calling `edit_video` with unmerged overlapping boundaries will produce physically cut clips that genuinely contain neighboring shots' frames.
   - **Verify the boundaries after cutting**: `edit_video` currently cuts at whole-second precision only, so the boundaries themselves have room for error; after the clips are cut, take a quick look at whether the first and last frames match the content recorded for this shot in the ledger — if the tail frame is clearly already the next shot's picture, the boundary was computed wrong; go back, adjust the absolute timestamps, and re-cut. You must not take clips with inaccurate boundaries straight into Mode 1's reference input or frame-extraction repaint.

**Missed-cut correction**: After the fine-grained analysis is done, if there is still an obvious abrupt visual change inside a "shot" (black screen / sudden scene or character change), treat it as a signal of a missed cut — go back to that interval, re-analyze with a finer hint and re-cut, so the physical clips are split correctly; you must not merely state verbally in the repaint plan that "this segment will be handled in two halves" while leaving the physical files untouched.

## Shot Content Analysis and Ledger (after cutting, before strategy judgment; must be done and must be recorded)

Having cut the clips does not mean you can directly apply the decision table — the "number of subjects / motion amplitude / shot size / high-risk elements" needed by the "repaint strategy judgment" are only the narrow fields required to decide the frame-extraction strategy, not the full content of this shot. If you settle for just these narrow fields, the information needed later by "repainting keyframes per shot" and "generating the repaint video" (who exactly is in the frame, what they are doing, whether there is dialogue, what the emotion is) will have no unified, retrievable record source, and each step will re-interpret the original footage piecemeal on its own, easily leading to inconsistencies.

**Every shot must record the following fields (use `write_file_v2` to produce a shot ledger file, as the single source of truth that all subsequent steps jointly rely on)**:

| Field | Description |
|---|---|
| shot number + time interval | Corresponds to the clip node cut by `edit_video`; the duration of this time interval is a hard constraint on the generation duration in the "generate repaint video" step (see below), not a casual note |
| Number of subjects / subject position & composition / motion amplitude / shot size / high-risk elements | Decision fields for the "repaint strategy judgment"; "subject position & composition" records the subjects' spatial distribution in the frame (e.g., "single person centered", "two people distributed left and right"); like "shot size", it comes from `analyze_video`'s structured output and must not be omitted |
| Camera movement | Static / push-in / pull-out / pan / track / follow — when the camera itself is moving, the frame composition keeps changing even if the subjects' motion amplitude is small; this field is supplementary evidence for deciding in the "repaint strategy judgment" whether to go with "multi-frame repaint" (see below) |
| Characters present | Who exactly they are; if it is a recurring important character, mark it so the "important character/scene anchor source confirmation" can reference it directly |
| Key actions/story beats | What actually happens in this shot; the basis for "action and emotion beats continuing from the original footage" in "generate repaint video" |
| Dialogue/lines | Record the characters' lines/narration in this shot verbatim; if there is no dialogue, honestly record "no dialogue" — changing the art style does not mean changing the voice, and this audio content must carry over when generating the new video |
| BGM/sound effects | The emotional tone of the background music and key sound effects (e.g., drumbeats, spell sounds, ambient noise) — likewise a record needed for "carrying over the original footage's audio layer", not just about the visuals |
| Key narrative information | Facial reactions, handheld props, on-scene text clues, etc. — these are exactly the fields the "content preservation" item in the "consistency check" watches |
| Scene identifier | Used to judge whether it continues in the same scene as the previous shot (deciding whether to use the previous shot's repainted tail frame as extra reference) |

**Record sources**: Video input → extract these fields from `analyze_video`'s structured output; storyboard/image input → extract them from the existing descriptions; when fields are incomplete, record faithfully based on the currently available information, without fabricating. Once this ledger is built, the "repaint strategy judgment" pulls the corresponding fields directly from the ledger to make decisions, without going back to re-read the original analysis results.

## Repaint Strategy Judgment (per shot, decide the frame-extraction/reference scheme; multiple selections allowed)
`aspect-reframe` decides "how to recompose" shot by shot; this skill decides "how to re-extract frames, how many frames are needed, and whether extra anchoring is required" shot by shot — the pipelines are similar, but art-style restyling has to worry about one extra layer, "redraw distortion," so both the decision dimensions and the strategies are finer-grained. Decisions are based on fields in the ledger: **subject count** (single person / two people / group of three or more), **subject motion amplitude** (static or slight / medium such as walking or gestures / large such as running, fighting, or fast displacement), **shot scale** (wide & full shots / medium-close shots / close-ups), **high-risk elements** (whether it contains hand close-ups, on-screen text, or intricate complex props — these are the categories where generative redraw most easily distorts), and **camera movement** (static / push / pull / pan / track / follow — used only to supplement the judgment of whether "multi-frame restyle" is needed, see below). The decision result (matched strategy + the number and positions of frames to extract) is appended back into the same shot ledger; there is no need to open a separate "plan sheet."

The four strategies are not mutually exclusive; a single shot may match multiple at once:

- **Single-frame restyle (default)**: static or slight motion, single person, or scene-dominated shots — just extract one frame from the middle of the shot and run image-to-image on it, with the style bible + the corresponding character/scene anchor as auxiliary references. Lowest cost; prefer classifying shots into this category.
- **Multi-frame restyle** (triggered when the subject motion amplitude is large **or** the camera movement itself is a continuously changing movement like push/pull/pan/track/follow): whether the character's actions are large or the camera itself is moving, the frame composition keeps changing throughout the shot, and a single frame cannot anchor the style of the whole process — when `generate_video_v3` hallucinates the intermediate frames, the art style easily drifts (from the restyled keyframes to the intermediate states, the style gradually goes off track). Handling: additionally extract 2–3 frames at the "opening pose / key action point / closing pose," restyle each one separately, and feed this set of restyled keyframes together as the generation reference sequence, rather than providing just one frame as the fallback.
- **Multi-character coordinated anchoring** (triggered when two or more people share the frame): the restyle prompt must explicitly reference each present character's own style anchor simultaneously, distinguished with directional words (e.g., "the character on the left of the frame references {{Anchor_A}}, the character on the right references {{Anchor_B}}"), to prevent characters from being swapped after restyling, or one character's anchor failing to take effect — this is exactly the same class of problem the "multi-character anti-duplication" rule solves, now applied at the individual-shot decision level. Group shots of three or more are higher risk, so the pause-point spot-check density should be raised accordingly.
- **High-risk element reinforcement** (triggered when the shot contains hand close-ups / on-screen text / intricate complex props): the restyle prompt must contain explicit constraint descriptions for these elements (e.g., "keep the finger count correct," "the prop shape must match the original footage"); during the "consistency check" phase, run through these shots separately — do not let a fatal flaw like hand distortion slip through just because the overall verdict reached "usable grade."

**Decision table**:

| Subject count | Motion amplitude | Shot scale | High-risk elements | Matched strategy |
|---|---|---|---|---|
| Single person / scene-dominated | Static / slight | Any | None | Single-frame restyle |
| Any | Large | Any | Any | Multi-frame restyle (stacked with other matched strategies) |
| Two or more people | Any | Any | Any | Multi-character coordinated anchoring (stacked with other matched strategies) |
| Any | Any | Close-up / close shot | Contains hands / text / complex props | High-risk element reinforcement (stacked with other matched strategies) |

The table above has no separate "camera movement" column — it is not an independent decision dimension, only a supplementary trigger condition for "multi-frame restyle": **when the subject motion amplitude is static/slight but the camera movement is a continuously changing movement such as push/pull/pan/track/follow, multi-frame restyle is matched all the same**, because the frame composition keeps changing with the camera's movement — the same risk as the subject moving a lot on its own, just from a different source. Only when both the camera and the subject are "fixed/static" does it truly fall into single-frame restyle.

**Common misjudgments, corrected**: ① Restricting "multi-frame restyle" to shots with genuinely large motion — force-fitting multi-frame restyle onto a static-dialogue shot with a fixed camera wastes cost, and a single frame is enough; but camera movement itself (even if the subject barely moves) does not count as "static," so those shots likewise need multi-frame. ② Multi-character coordinated anchoring must not be skimped into "they all have character anchors anyway, one line will do" — different characters must be precisely mapped to their respective anchors using directional words; a vague reference is as good as none. ③ High-risk element reinforcement is not finished by tacking on an extra line like "hands should look normal" — write concrete constraints for the specific elements (how many fingers, the prop's specific shape); generic constraints will not be properly executed by the model.

## Confirming the source of important character/scene anchors (before generating style anchors, where the anchor's content basis comes from)

The generation quality of character style anchors and scene style anchors directly determines whole-film consistency. **Do not carelessly set the anchor based on a one-sided description from a single shot where that character/scene appears** — a single shot may only capture a profile, a back view, or a wide shot, with incomplete information; if you generate the anchor from such a one-sided description, every later shot referencing that anchor inherits the inaccurate starting point, and the rework cost far exceeds asking one more question at the start. Before generating an anchor, for each recurring important character/scene, confirm the source of the content basis in this priority order:

1. **Script / character design doc / art design**: if the user uploaded a script or a character/art design document, extract the character's appearance description (facial features / hairstyle / body type / clothing / signature traits) and the scene description (spatial structure / lighting / color tone / key furnishings) from the text as the content basis for anchor generation — this path has no corresponding actual footage, so it can only go through pure text generation.
2. **Existing reference images**: if the user already has reference images of that character/scene (e.g., character or scene design sheets produced by a previous project), ask directly whether they can be uploaded and reused — no need to regenerate.
3. **Full-film search-based analysis (fallback; use only when neither of the above is available)**: run a separate full-film search for that character/scene and **capture real screenshots**, rather than just synthesizing a paragraph of text description — text retelling alone loses detail; actual screenshots are the most reliable basis for identity. **A character's style anchor cannot be generated from just one captured frame**: a character anchor is a set of 4 views (front, 3/4 side, full side profile, back — see "Core mechanism"), so collect screenshots to cover these 4 angles as much as possible, and prioritize frames where the full body is in frame; only fall back to half-body/close-up supplements when the film genuinely has no full-body shots; if a given angle genuinely has no corresponding footage in the film (e.g., no back-view shots), that angle simply goes through pure text generation — do not get stuck on that one angle just to gather real screenshots — the more complete the multi-angle, full-body raw screenshots are, the less likely the character anchor later redrawn per the style bible will have to blindly guess at un-photographed angles. The same applies to scenes: cover as many different camera positions/angles as possible to reconstruct the complete spatial structure. Before settling on each candidate screenshot, first check whether it is usable (clear with no motion blur, subject not excessively cropped or occluded, angle recognizable) — unusable candidates must not be settled for; re-capture at other time points near that angle, and if you truly cannot gather enough, honestly inform the user that coverage is incomplete.

**How the style anchor is generated varies by source**: sources 2 and 3 (existing reference images / full-film search screenshots) both yield real images; when generating character/scene style anchors in "Core mechanism," you should **feed that actual screenshot in as the image input** and redraw on its basis per the style bible (image-to-image), rather than discarding the screenshot and generating from scratch with text alone — a real screenshot locks in details like face shape, hairstyle, clothing, and scene furnishings, which text descriptions cannot achieve at that precision. Only source 1 (pure text script/design docs, with no corresponding actual footage) goes through pure text generation. Minor / one-off characters and scenes do not need this pipeline — just generate directly from the current shot's description; do not slow down minor content by running a finicky full-film search-based analysis.

## Core mechanism: first establish the "style bible + character/scene anchors," then batch restyle (mandatory prerequisite, cannot be skipped, required for both generation modes)
Regenerating each shot independently, the biggest enemy is **cross-shot jumping**—the same character having different faces in shots 3 and 8, the same scene having different spatial structures or color tones across different shots. This is the industry-wide recognized hardest-to-solve temporal consistency problem, and it is especially pronounced in this environment's "generate each shot separately" mode. The only effective suppression method is to lock down "style" and "character/scene appearance" as reusable anchors before batch generation:

1. **Style Bible** (written to a file via `write_file_v2`): Use text to lock down all key attributes of the target art style—line work (thickness/whether outlines are present), coloring method (cel-shaded flat / impasto / watercolor), color saturation and tonal tendency, lighting style, facial feature proportions and era of art style, material texture (when converting 2D to 3D, the rendering style must be defined especially clearly: toon shading / realistic PBR / clay feel). This file is the source of the style section for every subsequent generation prompt, ensuring the style description is reused word-for-word throughout the entire film.
2. **Character style anchors** (one set of **4 views** per recurring major character: front, 3/4 side, full side, back, via `generate_image_v3`): Not just one image—a single-angle anchor gives no basis when a downstream shot needs a reference from another angle, and the model can only guess, which is precisely one of the common triggers of cross-shot character drift. Content basis follows the information obtained through "anchor source confirmation" above—when actual screenshots exist (existing reference images/full-film retrieval screenshots), prioritize using screenshots of the corresponding angles for separate image-to-image redraws; only when there is no actual footage (pure text script/settings) use pure text generation; if among the 4 angles there is one for which a source image truly cannot be found (e.g., no back-view shots in the entire film), generate that one angle via pure text—no need to abandon that angle just to have a real screenshot. After approval, this set of 4 views serves as the visual anchor for that character across all shots; whichever angle a specific shot needs, reference that image. Once a character is anchored, all subsequent shots are generated using this anchor as reference, rather than improvising the character's appearance anew for each shot.
3. **Scene style anchors** (one per recurring major scene, via `generate_image_v3`): Similarly based on the information from anchor source confirmation (use screenshots for image-to-image when available; pure text generation only otherwise), generate a scene reference image in the target art style (spatial structure, key furnishings, lighting, color tone), and after approval reuse it as the visual anchor for every shot in which that scene appears—do not let the same scene have a unified art style across different shots while its spatial structure/furnishings are drawn independently in each.

This is the equivalent implementation of "anchor frames / cross-frame consistency" in this environment. Batch generating without confirming this step is equivalent to gambling that the art style and appearance of dozens of shots will automatically be consistent—they won't. Redoing one anchor image here is far cheaper than discovering whole-film character drift after batch generation and starting over.

## Style Category Differences (Asymmetric Risks and Handling)

- **Live-action to anime / realistic to 2D**: The most mature, most common, and lowest-risk. The core is "abstracting while preserving identity features"—facial features, hairstyle, body type, and signature clothing should correspond to the real person, but be redrawn in the target animation style. The main difficulty is cross-shot character consistency, solved by character style anchors.
- **Conversion between different anime/manga styles** (e.g., Japanese anime style ↔ Chinese impasto, cel shading ↔ watercolor): Feasible; essentially swapping in a new Style Bible and regenerating. The difficulty lies in original fans' sensitivity to "is this still the same character," so the character anchor must preserve the original character's recognizable memory points (hair color, eye color, signature accessories) under the new style.
- **2D/live-action to toon-shaded 3D (e.g., Pixar style)**: **Medium risk, with concrete usable reference techniques** (see "Pixar 3D Toon Rendering Reference Techniques" for details). Unlike realistic 3D: the rounded modeling of toon shading itself has higher tolerance for identity drift (audiences' threshold for judging "does it look like the person" is more lenient than for realistic 3D), and combined with multi-angle character portrait anchors, the success rate is notably better than pure realistic 3D.
- **2D/live-action to realistic 3D rendering** (non-stylized, e.g., realistic CG): **Highest risk; no mature solution found in research to date**. The probability of character identity drift and spatial structure inconsistency is significantly higher than the previous categories. In handling: the character style anchor step must be done more heavily (may need to generate multi-angle anchor images for one character to confirm 3D consistency), pause points should be denser, and the user **must be told in advance that this category does not guarantee first-pass success and has a high rework rate**.
- **Conversion to live-action/realistic style**: This skill **does not preset a style lexicon or constraint rules for this category**—the judgment criteria for realistic live-action are the user's specific descriptions at the moment (desired lighting, texture, atmosphere); generate directly according to the user's requirements without applying any preset "realistic style Bible" template. This is a deliberate opposite choice from the lexicon-accumulation approach of the other categories: realistic live-action has too much variation space, and any preset template easily comes across as rigid.

**Pixar 3D Toon Rendering Reference Techniques** (prioritize when converting to 3D toon rendering; sourced from research on skills generating similar styles—concrete engineering details that can be directly applied):
- **Texture words**: Marked sense of rounded modeling, clean backgrounds, facial feature descriptions must be detailed and thorough (hair color/length/hairstyle name, eye color/nose features/lip features/face shape, plus itemized notes on special features like "no tail" "no wings")—to judge whether a character anchor image is qualified, check whether all of these items match the original character.
- **Multi-angle character portraits**: This skill now requires character anchors to be a set of 4 views for all style categories (see "Core Mechanisms"); the Pixar 3D toon rendering category only adds one specific requirement on top of this—beyond the 4 views, the front-facing portrait must additionally be confirmed as a half-body shot with a calm expression, and the one covering the side-shooting angle that appears most frequently in the video must be clear and recognizable; do not casually generate any image just to check the box.

## Multi-Character/Prop/Copyright Handling Details (Cross-Style, Not Limited to 3D)

The following items are not techniques for a specific art style; they are engineering details that any style conversion involving multiple characters, props, or real people/brands should have:

- **Multi-character anti-duplication**: The more characters in the same shot, the higher the risk of "clones/duplicates," requiring explicit anti-duplication declarations in the prompt—with 3 or more people, write "A, B, and C in the frame each appear only once; no duplicate characters or character clones may appear"; with 5 or more, further strengthen the wording (name each one + "strictly forbidden to appear two or more times"), and prefer switching to panel-style close-ups shown in sequence rather than forcing everyone into a single panoramic group shot. This is the same thing as "multi-character collaborative anchoring" in "style conversion strategy determination"—here it is the general rule; there it is the determination applied to a specific shot.
- **Prop single-face principle**: Prop-type anchor images show only one face (choose either front or back; the display state—laid flat/held/open—must be clearly stated); simultaneous clarity on both front and back is not required; a combined "character + prop" image cannot be used as a reference image for video generation—props need their own separate anchors.
- **Copyright and real people/brands handling**: When real star/celebrity names or specific event/brand names are involved, substitute descriptive language instead of writing them directly (e.g., replace a real player's name with "a certain player" plus concretely recognizable visual features such as "red No. 7 jersey"), avoiding copyright risk while retaining recognizability through description. If a character/scene anchor triggers copyright restrictions and cannot be generated, switch to a pure text description of the character/scene features without passing in an image reference.

## Temporal Consistency (This Skill's Core Quality Bottleneck, Not an Add-On)

Repeatedly confirmed in research: temporal consistency (no jumping frame-to-frame/shot-to-shot) is the number one unsolved problem of AI-stylized video to date; even commercial solutions achieve only partial mitigation. This environment generates each shot independently and naturally has no cross-frame propagation mechanism, so it can only rely on **forward anchoring + post-hoc checking** clamping from both ends:

- Forward: the Style Bible ensures consistent style descriptions, character anchors ensure consistent appearances (pause point 4); shots with large motion magnitudes additionally go through "multi-frame style conversion" to reduce the risk of a single frame failing to cover the entire action.
- Post-hoc: after compositing, compare shot by shot; once cross-shot character drift or art style intensity jumping appears, return to the "per-shot keyframe style conversion" step and regenerate the problem shots using the same character anchor, rather than accepting the jumping.
- Honest expectation: even so, you will not achieve the "silky smoothness between frames" of traditional frame-by-frame transfer; what we aim for is "each shot looks right on its own, and the characters and art style stay coherent when viewed in sequence" — not seamless, streaming-grade consistency. This expectation must be aligned with the user before work begins.

## Consistency Check (three-tier grading, not binary pass/fail)

After each batch of shots is redrawn, review it against the six items below and assign a **three-tier grade**:

| Check item | What to look at |
|---|---|
| Character identity preserved | After redrawing, the character can still be traced back to the original (hairstyle/hair color/eye color/signature outfit/body shape have not drifted) |
| Scene consistency | Whether the same scene keeps a consistent spatial structure/key furnishings/lighting and color tone across different shots, all matching the same scene style anchor |
| Art style uniformity | Consistent line work/coloring/color tone/lighting and shadow style across the whole piece (all derived from the same style bible) |
| Content preserved | The original shot's composition, actions, emotions, and key props are still present in the redrawn version |
| Cross-shot temporal consistency | When adjacent shots are viewed together, the characters and art style flow continuously with no obvious jumps |
| High-risk elements | For shots flagged under "high-risk element reinforcement", whether hands/text/prop forms are correct — not let slide just because the overall verdict is "usable tier" |
| Dialogue/sound fidelity | `generate_video_v3` has no original-audio-track passthrough capability; audio is regenerated end-to-end together with the visuals — check whether the dialogue text in the generated video matches the ledger record verbatim (not rewritten/replaced/dropped), whether the speaking pace fills the shot's duration, and whether the emotional tone of the BGM/SFX matches the ledger record |

- **Error tier**: unrecognizable as the same character; obvious spatial-structure inconsistency for the same scene across different shots; loss of key narrative information; clearly wrong actions or emotions; obvious distortion of high-risk elements (e.g., wrong number of fingers); **dialogue rewritten into different content or obviously omitted, speaking pace clearly mismatched with the duration** — **discard and redo in the background, without showing it to the user**. In Mode 2, go back to the "per-shot redraw of keyframes" step, redraw the problem shot's keyframes using the existing character/scene anchors (plus the tail frame of the previous shot in the same scene), then regenerate the video; in Mode 1, go directly back to the "generate redrawn video" step, adjust the prompt, and regenerate — no need to redraw keyframes. If the error keeps recurring on the same character/scene, first go back to "key character/scene anchor source confirmation" to check whether the anchor itself lacks sufficient source information; if it keeps recurring on the same category of large-motion shots, check whether such a shot should have been judged "multi-frame redraw" but was judged as single-frame.
- **Usable tier**: no fatal flaws, but the art style's intensity deviates slightly and cross-shot transitions aren't smooth enough — **show it to the user and ask whether to accept or request a redo**.
- **Excellent tier**: all six items ideal — keep it directly and proceed to compositing.

Don't leave error-tier issues to be discovered only after compositing; and don't repeatedly go back to the user to confirm excellent-tier results.
